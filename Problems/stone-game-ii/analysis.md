# 1140. Stone Game II - Solution Analysis

## Problem Understanding
Alice and Bob take turns removing stones from the front of a row of piles. On a turn, a player takes the first `X` piles where `1 ≤ X ≤ 2M`, then updates `M = max(M, X)` (initially `M = 1`). Both play optimally to maximize their own total. The task is to return the maximum stones Alice can obtain. The constraints (`n ≤ 100`, positive pile values) allow an `O(n³)` dynamic programming solution.

## Approach
The solution uses **top-down dynamic programming with memoization** (a classic minimax game-theory pattern) combined with **suffix sums** for O(1) range-sum queries. The state is `(i, M)` representing the maximum stones the current player can collect from `piles[i:]` given the current `M`. The brute-force approach would explore all possible sequences of moves, which is exponential. The DP reduces this to `O(n²)` states, each evaluating up to `2M` transitions, yielding `O(n³)` time. The key insight: the current player's optimal score equals the total remaining stones minus the opponent's optimal score from the resulting state.

## Algorithm
1. Compute `suffix[i] = sum(piles[i:])` for `i = 0..n` (with `suffix[n] = 0`).
2. Define a memoized recursive function `dfs(i, M)`:
   - If `i ≥ n`: return `0` (no piles left).
   - If `i + 2*M ≥ n`: the current player can take all remaining piles; return `suffix[i]`.
   - Otherwise, for each `X` from `1` to `2*M`:
     - Compute `candidate = suffix[i] - dfs(i + X, max(M, X))`.
   - Return the maximum `candidate`.
3. Return `dfs(0, 1)`.

## Line-by-Line Explanation
- `n = len(piles)`: number of piles.
- `suffix = [0] * (n + 1)`: array to hold suffix sums.
- `for i in range(n - 1, -1, -1): suffix[i] = suffix[i + 1] + piles[i]`: builds suffix sums from right to left.
- `@lru_cache(None)`: memoizes `dfs` calls to avoid recomputation.
- `def dfs(i: int, M: int) -> int:`: returns max stones current player can get from index `i` with parameter `M`.
- `if i >= n: return 0`: base case, no piles left.
- `if i + 2 * M >= n: return suffix[i]`: current player can take all remaining piles in one move.
- `ans = 0`: will hold the best outcome for the current player.
- `for X in range(1, 2 * M + 1):`: tries every legal number of piles to take.
- `ans = max(ans, suffix[i] - dfs(i + X, max(M, X)))`: current player's gain = total remaining stones minus opponent's optimal gain from the new state.
- `return ans`: best achievable score from this state.
- `return dfs(0, 1)`: starts the game with Alice at index 0 and `M = 1`.

## Complexity
- **Time:** `O(n³)`. There are `O(n²)` distinct `(i, M)` states (`0 ≤ i < n`, `1 ≤ M ≤ n`). Each state iterates up to `2M = O(n)` values of `X`. With `n ≤ 100`, this is well within limits.
- **Space:** `O(n²)` for the memoization cache (at most `n²` entries) plus `O(n)` for the suffix array.

## Edge Cases
- **Single pile (`n = 1`):** `i + 2M = 0 + 2 ≥ 1` triggers the early return, correctly giving Alice the only pile.
- **All piles equal:** Handled naturally; the DP explores all splits.
- **Maximum `n = 100`:** The `O(n³)` runtime (~1e6 operations) and `O(n²)` memory (~10k entries) are easily acceptable.
- **Already sorted / reverse sorted:** Order does not affect correctness; the game always proceeds from the front.
- **No valid answer:** The game always terminates because `X ≥ 1` reduces the remaining piles each turn.

## Possible Improvements
The solution is already optimal for the given constraints. Converting to bottom-up DP would eliminate recursion overhead but is unnecessary for `n = 100`. Variable names (`suffix`, `dfs`, `i`, `M`, `X`, `ans`) are clear and idiomatic. No redundant passes or structures exist.
