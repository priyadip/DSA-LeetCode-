# 33. Search in Rotated Sorted Array - Solution Analysis

## Problem Understanding
Given a sorted array of distinct integers that has been rotated at an unknown pivot, find the index of a target value in O(log n) time. The rotation means the array consists of two sorted subarrays concatenated. If the target is absent, return -1. Constraints guarantee unique values and array length up to 5000, making O(log n) both necessary and sufficient.

## Approach
The solution uses **modified binary search**. The key insight: *in any rotated sorted array with distinct elements, at least one half (left or right of mid) is guaranteed to be strictly sorted*. By comparing `nums[left]` with `nums[mid]`, we identify the sorted half, then check whether the target lies within that half's range. If it does, we discard the other half; otherwise we discard the sorted half. This preserves the O(log n) guarantee of standard binary search while handling the rotation.

Brute force would scan linearly in O(n). Standard binary search fails because the array isn't globally sorted. The modification adds only constant-time range checks per iteration.

## Algorithm
1. Initialize `left = 0`, `right = len(nums) - 1`.
2. While `left <= right`:
   a. Compute `mid = (left + right) // 2`.
   b. If `nums[mid] == target`, return `mid`.
   c. If `nums[left] <= nums[mid]` (left half is sorted):
      - If `nums[left] <= target < nums[mid]`, target lies in left half → `right = mid - 1`.
      - Else target lies in right half → `left = mid + 1`.
   d. Else (right half is sorted):
      - If `nums[mid] < target <= nums[right]`, target lies in right half → `left = mid + 1`.
      - Else target lies in left half → `right = mid - 1`.
3. Loop exits without finding target → return `-1`.

## Line-by-Line Explanation
- `left = 0`: Start of search window.
- `right = len(nums) - 1`: End of search window.
- `while left <= right:`: Continue while window is non-empty.
- `mid = (left + right) // 2`: Middle index, biased left.
- `if nums[mid] == target: return mid`: Found target.
- `if nums[left] <= nums[mid]:`: Left half `[left..mid]` is sorted (no rotation pivot inside).
- `if nums[left] <= target < nums[mid]:`: Target falls in the sorted left half's value range.
- `right = mid - 1`: Discard right half including mid.
- `else: left = mid + 1`: Target not in left half → discard it.
- `else:`: Right half `[mid..right]` is sorted.
- `if nums[mid] < target <= nums[right]:`: Target falls in the sorted right half's value range.
- `left = mid + 1`: Discard left half including mid.
- `else: right = mid - 1`: Target not in right half → discard it.
- `return -1`: Exhausted search space without match.

## Dry Run
Example 1: `nums = [4,5,6,7,0,1,2]`, `target = 0`

| Step | left | right | mid | nums[mid] | Sorted half | Target in range? | Action |
|------|------|-------|-----|-----------|-------------|------------------|--------|
| 1 | 0 | 6 | 3 | 7 | left (4≤7) | 4≤0<7? No | left=4 |
| 2 | 4 | 6 | 5 | 1 | right (1≤2) | 1<0≤2? No | right=4 |
| 3 | 4 | 4 | 4 | 0 | left (0≤0) | 0≤0<0? No (but equality caught earlier) | return 4 |

At step 3, `nums[mid] == target` triggers immediate return.

## Complexity
- Time: O(log n), where n = len(nums). Each iteration halves the search space; all operations inside the loop are O(1).
- Space: O(1). Only a constant number of integer variables are used regardless of input size.

## Edge Cases
- **Single element array** (`len(nums) == 1`): Loop runs once, correctly returns 0 or -1.
- **No rotation** (array fully sorted): `nums[left] <= nums[mid]` always true; reduces to standard binary search.
- **Target at pivot** (minimum element): The right-half-sorted branch handles it because `nums[mid] < target <= nums[right]` correctly excludes the pivot when target is smaller than all right-half values.
- **Target not present**: Loop terminates when `left > right`, returns -1.
- **Maximum constraints** (n=5000): log₂(5000) ≈ 13 iterations, well within limits.

## Possible Improvements
The solution is already optimal for the given constraints: O(log n) time and O(1) space match the theoretical lower bound for comparison-based search in a rotated sorted array. Variable names are clear (`left`, `right`, `mid`). No redundant passes or structures exist. A minor stylistic alternative is using `left + (right - left) // 2` for `mid` to avoid theoretical overflow in languages with fixed-width integers, but Python's arbitrary-precision integers make this unnecessary.
